# M2 QA record

## Acceptance criteria

From [PLAN.md](../PLAN.md#m2--dashboard-in-claude-desktop):

- [ ] Dashboard served by the daemon: header bar (app picker, reload, restart), Logs and Activity tabs
- [ ] `flutterdeck init` writes config and the `.claude/launch.json` entry
- [ ] Hooks plus OS notifications
- [ ] FlutterDeck MCP server with `deck_status` and `get_logs`
- [ ] Accept: in Claude Desktop the dashboard sits next to chat and diff; Claude reloads through the Dart MCP server and the dashboard shows the reload; a notification appears when Claude finishes

Batch 1 has no dashboard UI, CLI, MCP server or hooks yet. It checks the daemon parts that these criteria depend on: cookie login (D1), fixed port per project (D2), the WebSocket heartbeat, the activity feed and reloads made by others (the "dashboard shows the reload" part of the last criterion).

**Findings for the developer (through the lead):**

- **F1 — a reload by someone else that fails to compile never shows in Activity.** Observed: no `IsolateReload` event and no activity entry. Expected (design D3 "reload failed", acceptance "dashboard shows the reload"): a failed reload entry. Cause: flutter_tools stops at the compile step and never asks the VM to reload, so the VM posts nothing. `docs/notes/dtd.md` says a failed event carries the compile error in `reloadFailureReason`; for a compile error that is not what happens with Flutter 3.44.6. Repro: steps B2 above.
- **F2 — a reload by someone else that the VM rejects shows as a success.** Observed: `IsolateReload` `status: "success"`, so Activity shows `{"ok":true,"source":"external"}` while Claude's tool call failed. Expected: a failure, or at least no success. flutter_tools reads `success: false` from the `reloadSources` report, but the event says success. Repro: steps B5–B6 above.
- With F1 and F2, the `Isolate` stream alone can't report failed reloads made by others. A design decision is needed (for example: show only successes from others and say so, or find another signal). This is a spec gap for the lead, not a QA fix.

Fixture: [`packages/connector-dart/src/testing/fixtures/isolate-reload.recorded.json`](../../packages/connector-dart/src/testing/fixtures/isolate-reload.recorded.json), built from run 2 (`36bb361`). It has a header with source, date, versions and findings, and one case per step: the raw `streamNotify` params (`streamId`, `event`) with real isolate and group ids. `ServiceExtensionAdded` events from the restart are left out (counted). No URIs, auth codes or tokens are in it (checked with `grep` for `ws://`, `http://`, `127.0.0.1`, `/Users/`, the user name and `token`).

Cleanup: `android-sample-app.sh down` stopped `flutter run` and the emulator the script booted, and removed the scratch app (both times). `adb devices` was empty after. The script did not reuse an emulator, so nothing stayed installed. Each script stopped its daemon and its `dart mcp-server` child and deleted its scratch `HOME`. ### Findings

- **B3-1 (daemon, pre-existing on `main`, low).** `projectIdentity` can read `~/.flutterdeck/ports.json` while `create()` is still writing it (`writeFile` with `flag: 'wx'` creates the file empty, then writes). The reader then throws "ports.json is damaged. Fix or delete it", and the message tells the user to delete the file. Seen once as the flaky test `keeps one salt when many first calls race on a new machine` under load. It can happen for real when the MCP server and a daemon start at the same moment on a new machine. Repro: run `pnpm check` while another full test run uses the machine. Expected: readers never see a half-written file (write a temp file, then `link`/`rename` it into place without replacing an existing one).
- **B3-2 (mcp, low).** If the daemon goes away within its first ~0.3 s, the start that `main.ts` began at server start never sees it answer. The next tool call joins that same pending start instead of spawning again, waits the full 10 s and returns "FlutterDeck daemon isn't running". Seen with a trace of every spawn (`qa-artifacts/M2/batch3/dbg-b3.mjs`, `trace-hook.cjs`): one spawn only; with the daemon up 3 s or 12 s first, the call spawns a new daemon and passes in ~220 ms. Repro: start the MCP server, wait until `runtime.json` appears, `POST /api/shutdown` at once, call `get_logs`.
- **B3-3 (mcp, medium, criterion C3).** When the configured port is held by another project's FlutterDeck (or another program) and this project has no `runtime.json`, Claude waits 10 s and gets "FlutterDeck daemon isn't running: run \`flutterdeck start\`". The real reason is only in the spawned daemon's stderr, which is discarded. Expected (design D2): "Another project's FlutterDeck is on this port" or "Another program uses port …". Repro: daemon for project B on port P; project A has `.flutterdeck/config.json` with port P and no `runtime.json`; start the MCP server for A; call `deck_status`.
- **B3-4 (spec question, low).** `regex` runs on message plus stack, so `$` and `^` anchor to the combined text. `^Request failed: \d{3}$` does not match a line that has a stack. The tool description says "matched against message and stack" only in the schema comment, not in what Claude reads. Question for the lead: should the description say so, or should the regex run on message and stack separately?
- **B3-5 (mcp masking, low).** An AWS secret access key after `aws_secret_access_key=` is not masked (40 chars of base64 with `/`). Design D4 lists "long secret-like strings". The `password=` rule masks the same shape. Suggest: treat `secret`, `secret_key`, `api_key`, `access_key` and similar names like `password=`.
- **Observation (not a product bug).** The PM's real `~/.flutterdeck/ports.json` exists (created 2026-10-14 22:19, before this QA session started at 22:50). QA did not create it and did not touch it. Every QA process here ran with a scratch `HOME`. The lead may want to ask who created it.
