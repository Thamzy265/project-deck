Notes on what the gate does by design (ADR 0005), which the first draft of this script expected otherwise:

- **Unbounded `WITH RECURSIVE` passes** with `recursive: true` (row 25). The gate only prepares, so a statement that would run forever still passes. Runtime limits belong to the backends (app `sqlite3_interrupt` after 5 s, sql.js in a terminable worker), which are not built yet. The worker restart after a timeout is shown with a statement that is slow to _prepare_ (row 26).
- **A trigger counts as a second table** in write mode (row 22). With the first draft's trigger on `orders`, `UPDATE orders …` was refused `multiple-tables`. So in an app whose tables have audit triggers, those tables can't be edited from the dashboard.
- **A view that selects a hidden column is refused whole** (row 20), even when the query reads only its other columns. This fails closed. See spec gap G1.

### Spec gaps (for the lead)

- **G1.** A view whose body selects a hidden column can't be read at all by Claude, even for its other columns (row 20). SQLite's authorizer reports every column of the view body. Is this the intended behaviour, or should a later batch narrow it (for example with the bytecode layer)? The design note says hidden columns are refused "through … views", but not that the whole view is refused.
- **G2.** Write mode refuses an edit whose trigger writes another table (row 22), as ADR 0005 says. Drift apps often have audit or `updated_at` triggers. Confirm that the Database tab should say why it can't edit such a table.
