Notes on what the gate does by design (ADR 0005), which the first draft of this script expected otherwise:

- **Unbounded `WITH RECURSIVE` passes** with `recursive: true` (row 25). The gate only prepares, so a statement that would run forever still passes. Runtime limits belong to the backends (app `sqlite3_interrupt` after 5 s, sql.js in a terminable worker), which are not built yet. The worker restart after a timeout is shown with a statement that is slow to _prepare_ (row 26).
- **A trigger counts as a second table** in write mode (row 22). With the first draft's trigger on `orders`, `UPDATE orders …` was refused `multiple-tables`. So in an app whose tables have audit triggers, those tables can't be edited from the dashboard.
- **A view that selects a hidden column is refused whole** (row 20), even when the query reads only its other columns. This fails closed. See spec gap G1.

### Finding F1 — app writes fail with "database is locked" during an inspector read on Android (fixed in `a77cb67`, re-verified below)

- **Observed:** while an inspector read that touches `orders` runs, tapping **Add order** fails at once (about 200–400 ms after the tap) with `Unhandled Exception: SqliteException(5): … database is locked … Causing statement: INSERT INTO "orders" ("item") VALUES (?)`. The order is lost. It happens with a runaway read (stopped at 5 s) and with a read that ends normally in 1.9 s (`SELECT count(*) FROM orders, (WITH RECURSIVE c(x) AS (SELECT 1 UNION ALL SELECT x + 1 FROM c LIMIT 400000) SELECT x FROM c)`). A runaway read that touches no table (`… FROM c` only) does not block the write.
- **Expected (design D-1, README):** the write waits for the read (at most 5 s + 1 s) and then succeeds.
- **Facts:** a temporary probe in the scratch copy (not in the repo) printed the app connection's pragmas: before the first inspector read `busy_timeout = 0`, after it `busy_timeout = 7000`, `journal_mode = delete`, `locking_mode = normal`. So `ensureAppBusyTimeout` ran, but the write still did not wait. The same scenario on macOS (temporary test with `openAppDb` + `DbReader`, both with sqlite3 3.7.1 and with an override to 3.5.2) passes: the write waits about 4.1 s and succeeds. Android `libsqlite3.so` from the build: compile options include `THREADSAFE=1`, `TEMP_STORE=2`, `ENABLE_BATCH_ATOMIC_WRITE`, `OMIT_AUTHORIZATION`, `OMIT_PROGRESS_CALLBACK`; it imports `nanosleep`. `/data` is ext4. With 111 short back-to-back `snapshot` reads and 20 taps, no write failed (20/20 saved).
- **Repro:** run the sample app on an API 34 emulator in debug. Call `ext.flutterdeck.drift.v1.query` with `db=sample` and `sql=WITH RECURSIVE c(x) AS (SELECT 1 UNION ALL SELECT x + 1 FROM c) SELECT count(*) FROM c, orders`. One second later tap **Add order**. `flutter run` logs the `database is locked` exception, and `SELECT count(*) FROM orders` does not go up.
- **Impact:** any long inspector read (Claude's `db_query`, a slow dashboard query) can make the user's own app writes fail on Android in debug builds. The app sees an unhandled exception that it would never see without FlutterDeck.

**Sample-app observation (not a package bug).** The sample app shows every order in one `Column` (not a lazy list). At 2,000 rows, frames took up to 6.8 s and the isolate group heap was 271 MB. Read timings in this state are skewed, because the extensions run on the busy main isolate. The 680 KB numbers above were taken with the app idle. If the M5 demo uses a large dataset, the sample's list should be lazy (`ListView.builder`).

### Findings

#### Q1 (minor) — the gate refuses `SELECT count(*)` over a recursive CTE with a misleading message

- **Observed:** `WITH RECURSIVE n(x) AS (SELECT 1 UNION ALL SELECT x + 1 FROM n LIMIT 5) SELECT count(*) FROM n` → 422 "n is not a table or view of this database." Same for `… SELECT count(*) FROM n, orders`. Same for the token and the cookie, on the live and the snapshot db.
- **Works:** `count(x)`, `sum(x)`, `max(x)`, `count(*) … WHERE x > 1`, `count(*) … GROUP BY x`, a non-recursive CTE with `count(*)`.
- **Expected:** a read-only statement is allowed, or refused with a reason that is true. It fails closed, so it is not a security issue. Claude and users often write `count(*)`.
