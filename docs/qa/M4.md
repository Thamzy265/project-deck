### Notes (minor, for the lead)

- **N1 (minor, `/db` wording).** The skill says "show the SQL it ran". In A1 Claude ran `… WHERE status = ?` with `params: ["pending"]`, but showed `… WHERE status = 'pending'`. The two are equivalent, but the SQL shown is not the exact SQL that ran. A2 does the same.
- **N2 (minor, `/check` wording).** In A5 the reload had worked (the screen showed v2), but the Next line still guessed: "If the marker text still shows the old value on screen, it is likely a `const` widget …". It is not wrong, but it is noise in an "all clear" report.
- **N3 (information).** A Flutter build error shows in **Runtime errors**. It does not count in **Logs**: A6 had "0 warnings, 0 errors", because Flutter prints the error at info level. This is consistent with the skill, but a user could read the Logs line as "nothing went wrong".
- **N4 (information).** With two DTDs running (the QA app's and Android Studio's), `/check` connected to the right one each time.

## Not observed

- **The harness deny of Monitor during `/db`.** Claude refused to call Monitor in 3 runs, so Claude Code's deny was never reached. During `/db`, `ToolSearch select:Monitor` still returned Monitor's schema (run 1). Bash, also in `disallowed-tools`, was denied by the harness, so the same mechanism very likely covers Monitor. Who can check: the reviewer or developer, from Claude Code docs or source, or with a test harness that calls the tool directly.
- **Claude Desktop and the PM's IDE.** QA did not install the dev marketplace into the PM's Claude settings. QA used `--plugin-dir` and the VM service stand-in instead. These checks are PM steps below.
- **The two-Dart-server case with prompts.** In headless mode the PM's `dart-flutter` plugin was present, but Claude always used the plugin's pre-approved Dart tools. If Desktop picks the other server, it asks before the Dart tool. That is expected (see `plugin/README.md`) and is not tested here.

It takes about 20 minutes. Run steps 1, 2, 3, 5 and 10 in one terminal, in order. Step 3 changes your Claude Code settings, and step 10 undoes it. The steps use the M4 worktree, where branch `feat/plugin-commands` is checked out. If the branch is already merged, use `~/Developer/Personal/project-deck` on `main` after `git pull` instead. QA ran steps 1, 2, 5 and 10 exactly as written in a clean shell, and ran steps 6–8 with `claude -p --plugin-dir` instead of Desktop.
