# flutterdeck_drift: facts and differences from the plan

Batch 2 of [the M3 design](../design/m3-drift-inspector.md) (`feat/flutterdeck-drift`). Checked on 16 Oct 2026 against the package sources in the pub cache: drift 2.35.2, drift_flutter 0.3.1, package:sqlite3 3.5.2 and 3.7.1, Flutter 3.44.6 (Dart 3.12.2).

## Facts checked

- **sqlite3 version.** Flutter 3.44.6 pins `meta` 1.18.0. package:sqlite3 3.6 and later need `hooks` ^2.2, which needs `record_use` ^1.0, which needs `meta` ^1.19. So a Flutter 3.44 app resolves at most sqlite3 3.5.x. The package asks for `sqlite3: ^3.5.2`; its own tests resolve 3.7.1, the sample app 3.5.2.
- **No `sqlite3_interrupt` or `sqlite3_limit` in package:sqlite3** (3.5.2 and 3.7.1). The package binds both itself with `@Native(assetId: 'package:sqlite3/src/ffi/libsqlite3.g.dart')`, the code asset package:sqlite3's build hook bundles (`lib/src/native.dart`). A test checks that both resolve. When package:sqlite3 compiles SQLite from source on Linux, its linker script exports only the symbols it uses itself; neither is among them, so the lookup fails there. The package then answers `unsupported` for queries (arbitrary SQL it could not stop) and still serves schema, snapshot and rows, which run only its own bounded SQL. The default (a prebuilt library) exports both.
- **`sqlite3_limit(SQLITE_LIMIT_LENGTH, n)`** never goes below 30 bytes (SQLite clamps it).
- **`checkNoTail`** throws `ArgumentError` (not `SqliteException`) for a second statement or for SQL that is only comments.
- **`PreparedStatement.close()`** and **`Database.autocommit`** exist in both 3.5.2 and 3.7.1.
- **Drift sets no busy timeout**, and drift_flutter sets no journal mode (rollback journal) and no busy timeout. drift_flutter sets `sqlite3.tempDirectory` (a process-wide setting), so the read connection's `temp_store=FILE` works on Android too.
- **Rollback-journal locks.** A reader holds a SHARED lock while a statement runs. An app writer without a busy timeout then fails at commit with "database is locked" (seen in the tests before the fix below). Some pragmas (for example `cache_size`) read the schema and so take a lock, so the read connection sets `busy_timeout` first.
- **`tableUpdates()`** is a broadcast stream of `Set<TableUpdate>`; `customInsert(updates:)` and `notifyUpdates` feed it; `customStatement` does not.
- **`driftDatabase()`** runs the connection in a background isolate (`NativeDatabase.createInBackground`). Errors come back wrapped in `DriftRemoteException` (from the experimental `drift/remote.dart`), whose `remoteCause` is the `SqliteException`.
- **Registering a service extension twice** throws `ArgumentError`. The build-mode test uses that to tell whether `register` registered anything in a VM started with `-Ddart.vm.product=true` or `-Ddart.vm.profile=true`.

## Differences from the plan

1. **Pure Dart package, no Flutter dependency.** `kDebugMode` is two `bool.fromEnvironment` constants; the package defines the same constant itself. This keeps the dependencies to drift and sqlite3, lets `dart test` run the tests, and lets the fixture recorder run a real VM service with DDS.
2. **Reads of databases not in WAL mode use a copy; the app's busy timeout covers the copy steps (D-1, PM decision 2026-10-16: "Read a copy (Recommended)").**
   - QA finding F1 (Android emulator): an app write that met a long inspector read failed at once with "database is locked", although the app's busy timeout was 7000 ms. Root cause: in debug builds `flutter run` turns on the Dart VM sampling profiler, which on Android and Linux sends SIGPROF to every Dart thread about once a millisecond, also while it is blocked in SQLite. SQLite's default busy handler sleeps with `nanosleep` and does not retry it after a signal, and it counts the sleep it asked for, not the time that passed. Measured on the emulator: `sqlite3_sleep(1000)` in a background isolate returned in 0–2 ms with the profiler on and in 1000 ms with `--no-enable-dart-profiling`; with the profiler off, the same repro's write waited and succeeded. On macOS the profiler pauses threads without signals, which is why the macOS tests passed. Both libraries have the same compile options.
   - So for databases not in WAL mode, the read isolate copies the file into a private in-memory database with the SQLite backup API, 64 pages per step, holding a shared lock only during a step, and runs schema, query, snapshot, rows and checkWrite on the copy. The copy is reused while `PRAGMA data_version` of the file connection is unchanged. A write by the app between steps makes SQLite restart the copy, so it is always consistent. Busy steps are retried by wall clock (2 ms waits), not through SQLite's busy handler.
   - Limits: 50 MB (above it, `too-large` with a hint to turn on WAL); the copy stops at the 5 s read budget, and a timeout interrupts both connections (file and copy).
   - Timings on macOS: 1 MB in under 1 ms, 10 MB in 8–10 ms, 44 MB in 35–40 ms; a reused copy costs about 1 ms.
   - WAL databases are read live.
   - The narrow debug-only busy timeout stays: `PRAGMA busy_timeout = 7000` on the app's own connection, only when the app has none and is not in WAL mode. It now only has to cover one copy step. It is one function, `ensureAppBusyTimeout` in `lib/src/service.dart`, with one call.
3. **Edits allow only `INSERT`, `REPLACE`, `UPDATE` and `DELETE`** on one table named without a schema. ADR 0005 lists a deny list (`ATTACH`, `DETACH`, `VACUUM`, `PRAGMA` writes, transaction control); an allowlist covers it, and the UI edits rows only.
4. **Extra `rows` extension** (from the brief) to read values by key for a diff; **extra error codes** `busy` and `not-allowed`.
5. **Blob cells** carry at most 64 KB of base64 (`truncated: true` beyond); keys carry whole blobs. **Non-finite doubles** are tagged `{type: 'real', value: 'Infinity' | '-Infinity' | 'NaN'}`, in cells and in keys. This is the agreed shape; core's `CellSchema` on `feat/db-core` gets the same variant.
6. **Write token.** The app checks only the token's shape (43 base64url characters) and that the token was not used before in this isolate. The set of used tokens lives in the app's isolate, so a hot restart (a new isolate) empties it. The app cannot tell a daemon-made token from any other. The daemon enforces single use (each confirm is bound to a server-made request id, refused after a hot restart) and stays the real control, through its dashboard-only route (design note S1).
7. **Schema and snapshot entries can carry an error.** A view or table the read connection can't use (a view that calls an app function such as Drift's `REGEXP`, a virtual table whose module is missing) gets `error: {code: 'unsupported', message}` with empty columns, instead of failing the whole call. Row counts are bounded too: at most 1,000,001 rows scanned per table and 2 s for all counts of one call; a table that gets no count keeps its columns, has no `rowCount` and gets an `error` (`too-large` or `timeout`). Core's `TableInfo` has the optional `error` field; `rowCount` stays optional, not nullable. The `db-drift` backend has to show these entries.
8. **Rowid keys for nullable primary keys.** A rowid table whose primary key may hold NULL (not `INTEGER PRIMARY KEY`, not declared `NOT NULL`) is keyed by rowid (`rowid: true`) in snapshot and rows, because SQLite lets such a key repeat NULL.
9. **Tables notified after an edit.** SQLite reports no list of the tables a statement changed, so after an edit the package notifies the target table, tables its triggers write to (any trigger on the table, whatever its event), and tables whose foreign keys cascade from it (`CASCADE`, `SET NULL`, `SET DEFAULT`), followed transitively. Naming a table that didn't change only costs a re-query. `REPLACE` and `INSERT OR REPLACE` are notified as updates.
10. **Read guard names.** SQLite takes a string literal where it expects a table name, so the guard reads single-quoted text as a name too. It refuses `pragma_database_list`, `dbstat`, `sqlite_dbpage` and every `pragma_*` table-valued function outside the read allowlist. Plain strings holding those words are refused as well.
