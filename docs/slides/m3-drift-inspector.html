The Drift database inspector

See your app’s database live next to Claude, ask Claude about the data, and see exactly what an action saved.

Use the arrow keys to move between slides · Print to save as PDF

Problem and users

Checking what the app saved is slow today

Who

A Flutter developer whose app stores data with Drift (SQLite), working with Claude.

The job they are doing

Tap something in the app, then check what was saved, find a row, or run a quick query.

Today’s pain

Drift’s DevTools extension lives in a separate browser window, has no “what changed” view, and Claude can’t see the data.

Success measure

A new row flashes on screen within 1 second; “what changed?” takes two clicks; Claude answers questions about the data.

Design note: docs/design/m3-drift-inspector.md · UI spec: docs/ui/m3-database-tab.md · ADRs 0004, 0005

Corrections to the plan from research: Drift keeps its file in app_flutter/ on Android (not databases/); snapshot copies need their change log merged.

Options

Live data without our package?

Option A: also use Drift’s own hook

  • Live view with no setup
  • Drift’s hook is internal and can change any release
  • It runs any SQL and has a “wipe database” action, so only our daemon guards it

Option B: our package only

  • One supported live path, with a guard inside the app too
  • Live needs one line in the app
  • Android still has a no-setup snapshot

Recommendation

Option B, because two independent guards protect the user’s data; we revisit after demo feedback.

Security

Claude must never change data by accident

Trust boundaries

  • Claude’s and the dashboard’s SQL → the app
  • Row contents → dashboard and Claude
  • A copied database file → our reader

Abuse cases

  • A row tells Claude to delete data
  • Tricky SQL that reads like a query but writes
  • A cloned project switches writes on
  • A release build exposes the database

Mitigations

  • Real SQLite checks every query in FlutterDeck, and the app checks again
  • Writes off by default; each write asks you
  • Text-only display, capped output
  • The package does nothing outside debug builds

Full list in the design note. ADR 0005: the two-layer read-only check.

Risks

The main risks

Risk Impact Mitigation
Drift or SQLite changes how things work Live view breaks after an update Versioned protocol; clear “update the package” message; recorded fixtures in tests
Masking misses personal data in free text Some personal data reaches Claude Hidden columns you choose; caps; clearly “best effort”
The sample app’s Drift setup needs network at build time CI or offline builds fail CI already has network; noted in the setup guide
