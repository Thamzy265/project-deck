Dashboard in Claude Desktop

Reload buttons, live logs and an activity feed next to Claude, plus a small FlutterDeck tool set Claude can call.

Use the arrow keys to move between slides · Print to save as PDF

Problem and users

M1 works, but only through curl

Who

A Flutter developer in Claude Desktop's Code tab, running the app from their IDE or terminal.

The job they are doing

Let Claude change the app, reload it, and see what happened in the logs, without switching windows.

Today's pain

Logs are in the IDE or a terminal, Android native logs are in yet another tool, and nothing shows what Claude did while you were away.

Success measure

Reload in one click or key; a new log line on screen in under 0.25 s; usable at 420 px wide; Claude can read the same logs.

Options

How the dashboard gets in and is found

A: login cookie + fixed port per project

  • No secret in any URL or page script
  • The Browser pane link never goes stale
  • If the port is busy, FlutterDeck says so instead of moving
  • Effort: small

B: key in the page + pane starts the daemon

  • Pane can start FlutterDeck by itself
  • Key readable by page scripts
  • Two ways to start the daemon can collide
  • Effort: medium

Recommendation

Option A, because it keeps secrets out of URLs and scripts and gives one stable dashboard link.

Data and privacy

App logs can hold your users' personal data

Data Purpose Retention Notes
App and Android log lines Show the developer what happens; let Claude debug Memory only; gone on Clear or daemon stop Sent to Claude only when Claude asks; best-effort masking by default (recommended)
Claude "waiting" message Activity entry and notification Memory only, last 500 events Claude's final answer text is never sent to FlutterDeck

Needs PM

How we treat logs sent to Claude (developer's own processing, or opt-in) · masking on by default? · DPIA screening: no triggers for FlutterDeck itself

Security

A web page must never drive your app

Trust boundaries

  • Any website you visit → the local daemon
  • Log lines and Claude's messages → dashboard and Claude
  • Daemon → OS notifier (if allowed)

Abuse cases

  • A site posts to 127.0.0.1 to reload your app
  • A log line with a script runs in the dashboard
  • A log line tells Claude to run a command
  • Crafted text breaks out of the notifier

Mitigations

  • Host and Origin checks, key or strict cookie on every call
  • Text-only rendering, strict content policy, no framing
  • Tools say logs are untrusted data
  • Fixed notifier scripts, text as arguments, tested payloads

Full list: design note, "Trust boundaries and abuse cases". The reviewer checks every route and the WebSocket against it.

Risks

The main risks

Risk Impact Mitigation
The Browser pane blocks cookies or framing in ways the docs don't say Dashboard can't log in inside Desktop QA tries it in Desktop in batch 2, before more UI is built
Plugin hooks or .mcp.json behave differently in Desktop than in the terminal (as we saw with the plugin pin) No Activity events or no tools in Desktop QA checks both with the desktop app's own Claude Code version
Masking hides a value the developer needed Claude misreads a log Masked values say so, e.g. [email masked]; one config switch turns masking off

Decisions needed

4 decisions for you

1. Dashboard login

Options: A cookie the page can't read, or B key written into the page

Recommendation: A, because no script or URL ever holds the key

2. Dashboard address

Options: A fixed port per project, pane attaches; or B pane starts FlutterDeck with any free port

Recommendation: A, because the link never goes stale and there is one way to start

3. OS notifications

Options: A allow three fixed notifier commands (changes a security rule); or B notifications inside the dashboard only

Recommendation: A, for crashed / reload failed / Claude waiting only. "Claude finished" stays with Desktop

4. Logs sent to Claude

Options: A mask personal data by default; or B no masking unless configured

Recommendation: A, because common patterns are masked by default (best effort, not a guarantee); one switch turns it off
